# M7：Agent 与人工确认

> 2026-11-18 进度：任务 1（client 支持 tools）已完成；任务 2（工具注册表）已完成（`list_ticket` 采用单数命名）；任务 3（Agent 循环）实现已给出并实测，待用户落地；任务 4~7 未开始。

> 预计 12-18 小时。目标：让模型不再只会"看着片段答题"，而是能**决定调用哪些工具、拿结果继续推理**；同时保证**任何写操作都必须先经人确认**才落库。

## 先理解：为什么需要这一层

现在的 `/ask` 是单轮的：检索 → 拼 prompt → 模型作答。它做不了这种事：

```text
用户：我订单 O001 收到时破了，能退吗，帮我登记一下
需要：查订单状态 → 查退款政策 → 生成工单草稿 → 人确认 → 落库
```

模型自己做不到"查订单"，除非我们告诉它**有哪些工具、参数长什么样**——这就是 function calling。但一旦模型能触发副作用（建工单、改状态），系统就从"问答"变成了"代理"，风险性质完全变了：

| 风险 | 例子 | 后果 |
|---|---|---|
| 参数幻觉 | 模型传 `order_id="O999"` | 轻则报错，重则改到别人的单 |
| 越权 | 用户 A 的会话里确认了用户 B 的工单 | 数据越界 |
| 重复执行 | 网络重试导致 confirm 发了两次 | 建出两张工单 |
| 死循环 | 模型反复调同一个工具 | 烧钱、超时 |

**所以 M7 的核心不是"更聪明"，而是"可控"**：读操作自动执行，写操作先提案、再确认、执行一次且只一次。

```text
用户消息 → 模型提议工具调用 → 只读？直接执行 → 结果回灌模型 → 继续
                              → 写操作？存成 pending，返回给用户确认
                                        → 确认后才真正执行
```

## 概念速览

### function calling 的完整往返

```text
① 请求：messages + tools=[{type:"function", function:{name, description, parameters(JSON Schema)}}]
② 响应：choices[0].message = {"role":"assistant", "content":null, "tool_calls":[
          {"id":"call_abc", "type":"function", "function":{"name":"get_order","arguments":"{\"order_id\":\"O001\"}"}}
        ]}
       注意：arguments 是 **JSON 字符串**，不是对象
③ 你要做的事：执行函数 → 追加两条消息：
   {"role":"assistant", ...tool_calls 原样放回}
   {"role":"tool", "tool_call_id":"call_abc", "content":"{\"status\":\"delivered\",...}"}
④ 再发一次请求，模型看到工具结果继续回答或调下一个工具
```

**模型从不执行函数**。它只输出"我想调用谁、参数是什么"，执行权在你手里。这正是可以加确认环节的原因。

### 读工具 vs 写工具

| 类型 | 例子 | 执行策略 |
|---|---|---|
| 读 | `search_knowledge`、`get_order`、`get_ticket`、`list_tickets` | 直接执行，把结果回灌 |
| 写 | `create_ticket`、`update_ticket_status` | 存成 pending，等人确认 |

分类不写在工具描述里让模型自己判断——**服务端维护白名单**。模型说"请直接建单"也没用。

### 状态机

```text
pending ──approve──> confirmed ──执行成功──> executed
   │                     └──────执行失败──> failed
   ├──reject──> rejected
   └──超时────> expired      （建议 30 分钟；超时的 pending 不可再确认）
```

合法迁移只有上表这些。`executed` 再 approve → 直接返回第一次的结果（幂等），不重复执行。

### 1. 扩展 `chat()` 支持工具调用

```python
def chat(messages, *, tools=None, temperature=0.2, max_tokens=None) -> dict:
    """返回 {"content", "tool_calls", "model", "usage"}，tool_calls 无工具时为空列表。"""
```

**要求**

- `messages` 现在会出现三种新角色：`assistant`（带 `tool_calls`）、`tool`（带 `tool_call_id`）。原样透传即可。
- `tools=None` 时**请求里不带 tools 字段**，且行为与 M3 完全一致（`rag_ask` 不能回归）。
- 放宽返回校验：`content` 为空**但** `tool_calls` 非空，是合法响应。
- `arguments` 是 JSON 字符串：用 `json.loads` 解析，失败抛 `LLMResponseError`（附截断原文）。
- 每个 `tool_call` 至少要能拿到 `id`、`function.name`、解析后的参数 dict；缺字段就抛 `LLMResponseError`。
- 保持现有的安全约束：报错只带状态码和截断文本，不带 header、不带 key。

#### 1.1 必须自己决定的事

| 决定 | 推荐 | 理由 |
|---|---|---|
| `arguments` 解析失败算谁的错 | `LLMResponseError` | 不是网络问题、不是配置问题；重试大概率还是错 |
| `tool_calls` 结构不合规怎么办 | 抛错，不猜测 | 猜出来的参数可能指向别人的订单 |
| 是否在 client 里校验参数 | **不校验** | client 只管协议；参数校验是工具层的职责（见任务 2） |
| 是否保留 `content` 为空即报错的旧逻辑 | 否，改成"content 与 tool_calls 至少一个" | 否则工具响应全被误判 |

#### 1.2 施工顺序

| 步 | 写什么 | 怎么验证 |
|---|---|---|
| 1 | **先探测**：一条最小的 `tools` 请求，确认供应商支持 | 看到 `tool_calls` 非空；返回 400 说明不支持，先解决这个 |
| 2 | 加 `tools` 参数只透传，不改解析 | 不带 tools 时 `rag_ask` 仍然正常 |
| 3 | 解析 `tool_calls`，`content` 为空不报错 | 打印出 `[("get_order", {"order_id":"O001"})]` |
| 4 | `arguments` 非法 JSON、缺字段的异常分支 | 用假响应（直接构造 dict）测，不花钱 |

**第 1 步不能省。** 如果供应商不支持 tools，后面五个任务的代码全是白写。

### 2. 工具定义与注册表 `app/agent/tools.py`

```python
READ_TOOLS: dict[str, ToolSpec]    # search_knowledge / get_order / get_ticket / list_tickets / get_customer
WRITE_TOOLS: dict[str, ToolSpec]   # create_ticket / update_ticket_status
def schemas_for_model() -> list[dict]   # 转成 OpenAI tools 格式
def execute_read(name: str, args: dict, conn) -> dict
```

每个工具包含：`name`、`description`、参数模型（Pydantic）、执行函数、是否写操作。

**要求**

- **工具描述写"什么时候用"，不写"是什么"**。模型选错工具几乎都是描述太含糊。
- 参数用 Pydantic 模型校验，**校验失败不要把异常抛给用户**，而是返回结构化错误给模型：

```json
{"ok": false, "error": "参数不合法", "fields": [{"loc": "order_id", "msg": "String should match pattern ..."}]}
```

模型看到这条可以改参数重试；用户看到的是"订单号格式不对"，而不是 500。

- **工具结果统一成 `{"ok": bool, ...}`**。模型需要能区分"查到了"和"查不到"。
- 业务异常（`NotFoundError` / `ValidationError`）在工具层就地转成 `ok:false`，不要往上层抛。

#### 2.1 必须自己决定的事

| 决定 | 推荐 | 理由 |
|---|---|---|
| 工具结果返回全字段还是摘要 | 摘要 + 关键字段 | 全字段会挤占上下文；但 `order_id`/`status`/`amount` 必须有 |
| 一个工具查不到时返回 `ok:false` 还是空结果 | `ok:false` + 原因 | 空结果模型会当成"没有数据"继续编 |
| 要不要给模型 `list_tickets(customer_id)` | 要 | 真实客服第一件事是看这个客户有没有相关工单 |
| 是否提供"通用 SQL"工具 | **绝对不要** | 等于把数据库交给模型 |

#### 2.2 施工顺序

| 步 | 写什么 | 怎么验证 |
|---|---|---|
| 1 | 只注册 `search_knowledge` 一个工具 | 直接调 `execute_read` 用 pytest 式打印验证 |
| 2 | 加四个读工具 + Pydantic 参数模型 | 传错参数拿到 `ok:false` 而不是抛异常 |
| 3 | `schemas_for_model()` | 打印出来的 JSON 能贴进 `/chat/completions` 的 tools |

### 3. Agent 循环（只读）`app/agent/loop.py`

```python
def run_agent(conn, *, session_id: str, message: str, max_steps: int = 5) -> dict:
    """返回 {"answer": str, "steps": [...], "pending": dict | None}"""
```

**要求**

- 维护消息列表：`system` → `user` → 循环里追加 `assistant`（带 tool_calls）和每个 `tool` 结果。
- 每次循环：调 `chat(messages, tools=...)` → 无 `tool_calls` 则返回 `answer`；有则执行 → 回灌 → 继续。
- **`max_steps` 必须存在**，超限返回"未能完成，请补充信息"，而不是继续烧钱。
- 遇到写工具：**不执行**，把 `{"tool": name, "arguments": args}` 作为 `pending` 返回，循环终止。
- 每步记录 `{"step", "tool", "args", "ok", "elapsed_ms"}`，为 M9 的 trace 打基础。

#### 3.1 必须自己决定的事

| 决定 | 推荐 | 理由 |
|---|---|---|
| `max_steps` 取多少 | 5 | 真实客服场景 2-3 步够用；5 足够兜住异常 |
| 超过上限返回什么 | 固定话术 + 已收集的步骤 | 让用户知道"卡在哪"，而不是空回复 |
| 工具失败后继续还是终止 | 继续（结果已回灌） | 模型可能换一个参数或换工具，这正是它的价值 |
| 同一工具同一参数重复调用 | 允许，但计数；≥2 次就中止 | 防死循环的最实际判据 |
| 是否把检索片段塞进 system | 不塞，改成工具结果 | 否则模型不知道该先检索 |

**这是 M7 的教学核心**：上一轮模型只能看到 `build_messages` 拼好的片段；现在片段变成模型按需调用的结果。对比两种做法在同一个问题上的差别。

#### 3.2 施工顺序

| 步 | 写什么 | 怎么验证 |
|---|---|---|
| 1 | 循环骨架，只有一个读工具 | 问"订单 O001 什么状态"→ 至少调一次 `get_order` |
| 2 | 加 `max_steps` 和步骤记录 | 人为把上限设成 1，确认能优雅退出 |
| 3 | 加写工具识别（只返回 pending，不执行） | 日志里能看到"提议创建工单"，数据库里没有新行 |

### 4. pending 落库 `app/db/schema.sql` + 仓库函数

```text
pending_actions(
  id TEXT PRIMARY KEY,          -- PA-xxxx
  session_id TEXT NOT NULL,
  tool_name TEXT NOT NULL,
  arguments TEXT NOT NULL,      -- JSON 字符串
  status TEXT NOT NULL,         -- pending/confirmed/executed/failed/rejected/expired
  created_at TEXT NOT NULL,
  decided_at TEXT,
  result TEXT                   -- 执行结果 JSON
)
```

**要求**

- 建表用 `CREATE TABLE IF NOT EXISTS`，`init_db` 自动带上。
- 仓库函数：`create_pending`、`get_pending`、`mark_decided`、`mark_result`。
- 写入 pending 时**就校验一遍工具名是否在白名单**——模型提议一个不存在的工具，不该进表。

#### 4.1 必须自己决定的事

| 决定 | 推荐 | 理由 |
|---|---|---|
| 状态放哪 | 数据库 | 见下方推导 |
| `arguments` 存 JSON 字符串还是拆列 | 字符串 | 不同工具参数不同；拆列就要改表 |
| 确认超时怎么实现 | `created_at` + 判断 | 别用定时任务；查询时判断更简单 |
| pending 是否也记录 session | 必须 | 确认时要用它做越权校验 |

**推导例：为什么不能放内存 dict**

```text
方案：PENDING = {} 模块级字典
① uvicorn --reload 改了代码 → 进程重启 → 所有待确认操作消失，用户点了"确认"得到 404
② 以后开多 worker（uvicorn --workers 2）→ 两个进程各有各的字典，确认请求落到另一个进程 → 404
③ 服务崩溃 → 用户已经看过的确认单丢了，无法审计
结论：待确认状态是**业务数据**，不是缓存，必须落库
```

### 5. 确认执行：状态机 + 幂等

```python
def confirm_pending(conn, *, pending_id: str, session_id: str, decision: str) -> dict:
```

**要求**

- `decision` 只能是 `approve` / `reject`（用 `Literal`，非法值 422）。
- 取 pending → 校验存在（否则 404）→ 校验 `session_id` 匹配（否则 404，不要用 403 暴露"这个 id 存在"）→ 校验状态是 `pending`。
- `pending` 且 `expire` 超时 → 置 `expired` 并返回 409。
- `executed` + approve → **返回第一次的 `result`，状态不变**。这是幂等。
- `rejected` + approve → 409。
- 执行写工具时：`actor` 服务端固定 `"api"`，`status` 不来自模型。
- 执行前后都要 `mark_*`，且**在同一个事务里**——不能执行成功但状态没更新。

#### 5.1 必须自己决定的事

| 决定 | 推荐 | 理由 |
|---|---|---|
| 幂等靠什么实现 | 状态 + `result` 字段 | 不需要额外的 idempotency_key；pending_id 本身就是键 |
| 执行失败怎么办 | `failed` + 记录错误 | 不能让状态停在 `confirmed`，否则永远无法重试也无法解释 |
| 失败后能否重新确认 | 不能（除非新提案） | 否则"失败→重试→成功"会变成两次副作用 |
| 越权返回 403 还是 404 | 404 | 403 等于确认"这个待办存在" |
| 用户拒绝是否要记录 | 要，`rejected` + `decided_at` | 审计和 M9 指标都要用 |

#### 5.2 施工顺序

| 步 | 写什么 | 怎么验证 |
|---|---|---|
| 1 | 只实现 approve + 正常执行 | 确认后工单真的出现在 `GET /tickets` |
| 2 | 幂等：同 id 再 confirm | 第二次返回相同 id，**数据库里只有一张单** |
| 3 | reject | 状态 `rejected`，数据库无新工单 |
| 4 | 越权 + 超时 + 非法状态迁移 | 三种 4xx 各触发一次 |

第 2 步是 M7 最容易被跳过、也最容易在真实事故里出现的一步。

### 6. 越权与参数防护

**要求**

- **执行前重新校验参数**，不信任模型：用任务 2 的 Pydantic 模型再跑一遍。
- 业务校验仍在仓库层（订单属于该客户、状态流转合法、客户存在）。
- 服务端固定字段：`actor`、`status=open`。
- 工具名白名单：不在 `READ_TOOLS | WRITE_TOOLS` 里 → 直接丢弃该 tool_call，并把错误回灌给模型。
- 所有写工具执行只能从 `confirm_pending` 一条路径进入，`execute_*` 不对外暴露 HTTP。
- 日志里记录 `pending_id`、`session_id`、工具名、参数摘要，**不记录 API Key、完整 header**。

#### 6.1 必须自己决定的事

| 决定 | 推荐 | 理由 |
|---|---|---|
| 模型传了白名单外的工具名 | 回灌 `ok:false` 给模型 | 直接 500 会让用户看到"服务错误" |
| `session_id` 谁生成 | 客户端生成 UUID | 服务端不需要会话存储；但确认时天然绑定 |
| 是否限制单个会话的 pending 数量 | 建议 ≤ 5 | 防模型刷单 |

**推导例：哪一层拦得住 `customer_id="C999"`**

```text
① 工具参数 Pydantic：C999 格式合法 → 拦不住
② 执行前再校验：同上 → 拦不住
③ 仓库 create_ticket：客户不存在 → NotFoundError → 拦住了
④ 确认环节：用户看到"为客户 C999 建单"会拒绝 → 拦住了（但依赖人）
结论：格式校验拦不住语义错误，业务规则必须在仓库层；人工确认是最后一道闸
```

### 7. HTTP 接口

```text
POST /agent/chat     {session_id, message}                    → {answer?, pending?, steps}
POST /agent/confirm  {pending_id, session_id, decision}       → {status, ticket?}
```

**要求**

- 两个都是 `def` 路由（理由同 M6）。
- `decision` 用 `Literal["approve","reject"]`。
- `/agent/chat` 返回 `pending` 时必须包含：`pending_id`、`tool`、`arguments`、`expires_at`，**足够用户判断要不要同意**。
- 错误走 M6 的 `errors.py`，不要新写一套。
- `/agent/chat` 慢（多步 LLM），默认 `timeout` 在文档里写清楚。

## 验收标准

- [ ] `chat(tools=...)` 能拿到并解析 `tool_calls`；`tools=None` 时 `rag_ask` 行为不变。
- [ ] 问"订单 O001 现在什么状态"，Agent 至少调用一次 `get_order`，答案里带真实状态。
- [ ] 问"帮我登记订单 O001 破损退款"，Agent 返回 `pending`，**数据库里没有新工单**。
- [ ] confirm approve 后工单落库，`events[0].actor == "api"`。
- [ ] **同一 pending_id approve 两次，只产生一张工单**，第二次返回相同结果。
- [ ] reject 后状态为 `rejected`，无新工单。
- [ ] 换一个 `session_id` 去 confirm → 404。
- [ ] 超过 30 分钟的 pending → 409（可用改 `created_at` 模拟，不必真等）。
- [ ] 模型提议 `customer_id="C999"` → 执行失败 `failed`，错误信息可读，不是 500。
- [ ] 工具名不在白名单 → 回灌 `ok:false`，Agent 能继续回答或优雅收尾。
- [ ] 模型反复调同一工具 → `max_steps` 或重复计数生效，不会无限循环。
- [ ] 任何响应/日志里没有 API Key、Authorization header、完整异常堆栈。

## 提示与坑

- **先把"探测"做好**：用一条手工构造的 `tools` 请求确认供应商支持，再写业务。很多 OpenAI 兼容网关对 tools 支持参差不齐。
- `arguments` 是字符串。90% 的解析错误都出在忘了 `json.loads`。
- 工具结果要**短**。把整段订单 JSON 塞回去，上下文会迅速膨胀，模型反而更糊涂。
- 别指望模型"应该知道"订单号格式。工具描述里给一个例子：`订单号形如 O001`。
- **pending 不是缓存**。任何"重启就丢"的实现都不能算完成。
- 幂等不是"加个判断"，是"重复请求返回同一个结果"。验收时要连点两次看数据库。
- 人工确认的界面文案很重要：要说清"将创建工单：客户 C001 / 订单 O001 / 标题 xxx"，而不是"确认执行 create_ticket"。
- 写工具的执行路径只有一条（`confirm_pending`）。如果发现别处也能建单，说明越权防护破了。
- `max_steps` 是最后兜底，不是主要手段；先保证工具描述清晰、结果可读。
