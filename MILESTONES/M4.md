# M4：RAG CLI 闭环

> 预计 10-15 小时。目标：把 M1 切好的 chunk 存进向量库，用户提问时检索 top-k 片段，拼进 `messages` 交给 M3 的 `chat()`，打印一段**带引用**的回答。

## 先理解：RAG 闭环缺的是哪两步

M1 只做了前两步，M3 只做了最后一步：

```text
1 加载  ✓ M1
2 切分  ✓ M1
3 建索引 ← M4
4 检索   ← M4
5 生成  ✓ M3（但还没接检索结果）
```

M4 把 3、4 补上，并让第 5 步真正用上前四步的产物。

```text
问题
 │
 ├─ embed(query) ──→ 在 Chroma 里找最相近的 chunk      ← 检索
 │                        │
 │                        ▼
 │                   拼进 messages 的 user 内容       ← 增强
 │                        │
 └──────────────────→ chat(messages) ──→ 带引用的回答  ← 生成
```

### 1. Embedding 封装 `app/rag/embedding.py`

```python
def get_model_name() -> str:
    """返回当前使用的 embedding 模型名。"""

def embed_texts(texts: list[str]) -> list[list[float]]:
    """批量把文本转成向量。"""

def embed_query(text: str) -> list[float]:
    """把一条查询转成向量。"""
```

**要求**

- 模型用 `BAAI/bge-small-zh-v1.5`（中文小模型，512 维，速度快）。**从本地目录加载**，不要用模型名联网拉取：

```python
MODEL_NAME = "BAAI/bge-small-zh-v1.5"
MODEL_DIR = PROJECT_ROOT / "models" / "bge-small-zh-v1.5"
```

路径不存在时给出明确提示（"模型目录不存在"），不要静默回退到联网下载——国内直连 huggingface.co 会卡很久。

- **模型只加载一次。** `SentenceTransformer(path)` 要几百毫秒到几秒，每次调用都新建会慢到无法接受。用模块级全局变量或 `functools.lru_cache` 缓存。
- 编码时用 `normalize_embeddings=True`。归一化后，向量内积就等于余弦相似度，后面算分才简单。
- `texts` 为空列表时直接返回 `[]`，不要调用模型。
- 返回值必须是 `list[list[float]]`：`model.encode()` 返回的是 numpy 数组，要 `.tolist()` 转掉，否则后面 JSON 序列化会失败。
- 可选：给查询加指令前缀 `"为这个句子生成表示以用于检索相关文章："`（bge 中文模型的推荐用法），但**只能加在 query 上，不能加在文档上**。

### 2. 向量库 `app/rag/index.py`

```python
def get_collection():
    """返回持久化的 Chroma collection。"""

def build_index(chunks: list[dict], *, reset: bool = False) -> int:
    """把 chunk 写进向量库，返回写入数量。"""
```

**要求**

- 用 `chromadb.PersistentClient(path=str(settings.chroma_dir))`。**不要用 `chromadb.Client()`**，那个是内存版，进程退出就没了。
- collection 名固定 `"knowledge"`，创建时加 `metadata={"hnsw:space": "cosine"}`，否则默认是 L2 距离，分数含义会变。
- **ID 必须确定性**：`f"{chunk['doc_id']}::{chunk['chunk_index']}"`。这样重复导入会覆盖同一条，而不是产生重复数据。
- `documents` 放 chunk 的 `text`；`metadatas` 放 `doc_id`、`title`、`section`、`chunk_index`、`source_path`。
- 元数据值只能是 `str` / `int` / `float` / `bool`，**不能是 `None` 或嵌套 dict**，否则 Chroma 报错。
- 分批写入（比如每批 64 条），一次写几千条容易卡住。
- `reset=True` 时先删掉同名 collection 再建。
- 幂等：连续运行两次 `build_index`，collection 里的条目数不变。

### 3. 检索 `app/rag/retriever.py`

```python
def search(query: str, *, top_k: int = 4) -> list[dict]:
    """返回最相关的若干片段。"""
```

返回结构：

```python
{
    "text": str,
    "doc_id": str,
    "title": str,
    "section": str,
    "chunk_index": int,
    "source_path": str,
    "score": float,      # 越大越相关
}
```

**要求**

- 查询向量用 `embed_query()` 生成，**不要复用 `embed_texts()`**（语义不同，以后加指令前缀也只在 query 上）。
- Chroma 用 cosine 距离返回 `distance`，换算成 `score = 1 - distance`。要在注释里写清楚为什么。
- 结果按 `score` 降序。
- collection 为空时抛出明确异常（提示先运行 `build_index`），不要静默返回空列表。

### 4. Prompt 拼装 `app/rag/prompt.py`

```python
def build_messages(question: str, hits: list[dict], *, system: str | None = None) -> list[dict]:
    """把检索结果和问题拼成 chat 接口要的 messages。"""
```

**要求**

- system 至少包含三条约束：
  1. 只依据提供的资料回答；
  2. 资料里没有就明说"资料中没有提到"，不要编；
  3. 引用时用 `[1]`、`[2]` 标注来源编号。
- user 内容结构：

```text
资料：
[1] （文档名 / 章节）
片段正文……

[2] （文档名 / 章节）
片段正文……


问题：<用户问题>
```

- `hits` 为空时也要能拼出合法 messages（提示模型没有检索到资料）。

### 5. CLI

**`scripts/build_index.py`**

```text
python -m scripts.build_index
python -m scripts.build_index --reset
```

- 加载 `data/knowledge/` → 切块 → 写向量库。
- 打印：文档数、chunk 总数、写入数量、耗时。
- `--reset` 先清空再建。
- 失败（目录不存在、没有文档）时退出码 1，错误走 stderr。

**`scripts/rag_ask.py`**

```text
python -m scripts.rag_ask "退款政策是什么？"
python -m scripts.rag_ask "..." --top-k 6
python -m scripts.rag_ask "..." --show-context
python -m scripts.rag_ask "..." --retrieval-only
python -m scripts.rag_ask "..." --mock
```

- 流程：检索 top-k → 拼 messages → `chat()` → 打印回答。
- `--show-context`：把命中的片段和分数打印到 **stderr**（不要污染 stdout）。
- `--retrieval-only`：只做检索并打印片段，不调用 LLM，退出码 0。**这是 M4 最重要的调试开关。**
- `--mock`：不联网，打印固定回答，用于验证 CLI 管线。
- 退出码：成功 0；配置/网络/知识库为空等错误 1；参数错误 2。
- 预期错误不打 traceback，`except LLMError` 统一翻译。
- 回答打印完后，在 stderr 追加一行引用来源，例如：

```text
引用：[1] 退款政策 / 退款时效；[2] 退款政策 / 不支持退款的情形
```

### 6. 引用校验（可选加分）

- 解析回答里出现的 `[n]`，检查 `n` 是否落在 1..len(hits) 范围内；
- 越界时在 stderr 提示"模型引用了不存在的片段编号"，不中断输出；
- 统计本次回答实际引用了几个片段，为 M9 的评测打基础。

## 提示

- **先别接 LLM。** 先做 `build_index` + `--retrieval-only`，确认"问退款能检索到退款政策的片段"，再接 `chat()`。检索错了，后面生成的回答全是错的，但错得很像真的。
- 首次运行会下载模型，卡在 `Loading weights` 是正常的；设置 `HF_ENDPOINT` 镜像会快很多。
- `chromadb.Client()` 是内存版，重启就没了；`PersistentClient` 才是落盘的。
- `model.encode()` 返回 numpy 数组，直接塞进 JSON 会报 `TypeError: Object of type ndarray is not JSON serializable`，要 `.tolist()`。
- 归一化（`normalize_embeddings=True`）后，`1 - cosine_distance` 才是可解释的相似度；不归一化时分数看起来会很怪。
- 元数据里 `chunk_index` 是 `int`，其它是 `str`；Chroma 不允许 `None`。
- 如果检索结果明显不相关，先看三件事：模型是否真加载了、是否归一化了、chunk 是不是切得太碎或太长。
- 如果回答内容对但引用编号不对，问题在 prompt 或拼装顺序，不在检索。
- `--show-context` 一定要写 stderr，否则 stdout 里混进片段，后面接入 API 时没法用。
- 不要把整篇文档塞进 prompt。`top_k` 默认 4，每个 chunk 已控制在 300-400 字，总量可控。
- 真实调用花钱，调试时 `--max-tokens 128` 先验证链路。
