## 先理解：作品化不是"写 README"

代码写完不等于作品。别人判断你的项目，实际靠三样东西：

| 别人会问 | 对应材料 |
|---|---|
| 这是什么、解决什么问题？ | README 开头 3 行 |
| 架构是怎么搭的？ | 架构图 + 模块职责 |
| 真能跑吗？ | 5 分钟 demo 步骤 + 预期输出 |
| 哪里做得不好？ | 限制说明 + 评测数据（诚实的） |
| 这些能力对应什么岗位要求？ | FDE 能力映射 |

**最难的是第 4 条**：多数作品集只写"实现了 XX"，不写"XX 在什么条件下会失效"。
后者才是工程判断力的证据。

## 交付物

```text
README.md               作品集级入口（3 行讲清是什么 + 架构图 + 快速开始 + 限制）
docs/architecture.md    架构、数据流、模块职责、关键设计决策与权衡
docs/demo.md            5 分钟演示流程，每步有预期输出
docs/fde-mapping.md     能力 → 项目证据映射
scripts/demo_walkthrough.py  半自动演示脚本（调用运行中的 API）
```

## 要求

### 1. 架构图用 Mermaid

GitHub 原生渲染。三层足够：**数据层 → 能力层 → 接口层 → 前端**。
标出两条不同的链路：RAG 问答（同步/流式）与 Agent（读工具自动、写工具确认）。

### 2. 关键决策要写"为什么"和"代价"

每一条都必须是**权衡**，不是功能列表：

```text
✅ 用 RRF 而不是分数加权：两路量纲不同；代价是丢失分数强度信息
✅ 写操作两阶段确认：防不可信输入触发副作用；代价是交互多一步
✅ 门槛默认关闭：评测集上分数重叠；代价是库外问题依赖 prompt 拒答
❌ 使用了 FastAPI（这不是决策，是选型）
```

### 3. 评测数据如实写

```text
hybrid 与 BM25 持平（hit@1 0.818，recall@4 1.000），未观测到融合增益
相关性门槛在 34 chunk 上不可分（0.5842 vs 0.5728）
```

**不要**写成"混合检索显著提升效果"。评委/面试官一眼能看出样本量和结论不匹配。

### 4. Demo 必须可复现

- 每条命令都能直接复制执行。
- 每步给出**预期输出**（状态码/字段），而不是"应该能成功"。
- 标注哪一步会花钱（调用模型），哪一步不花钱。

### 5. 限制要具体

```text
✅ 单机、无鉴权、session_id 可伪造（但只能确认自己的待办）
✅ Agent 无跨轮历史，"那帮我退了吧"会丢失指代
❌ 还有优化空间（等于没说）
```

## 验收标准

- [x] README 前 3 行能说清"是什么、给谁用、解决什么"。
- [x] 架构图在 GitHub 上能正常渲染（Mermaid 语法无误）。
- [x] 文档里有至少 5 条"决策 + 代价"。
- [x] 评测数字与实际脚本输出一致（可对照 `data/eval/report.md`）。
- [x] `docs/demo.md` 的每条命令可直接复制执行，标注是否花钱。
- [x] `scripts/demo_walkthrough.py` 在 API 未启动时给出明确提示，而不是堆栈。
- [x] 限制清单具体到"什么场景会失效"。
- [x] `docs/fde-mapping.md` 每条能力都指向具体文件或数据，不空谈。
- [x] 全仓库搜索不到真实 API Key / 密码。
- [x] 新读者从 README 出发，10 分钟内能跑起 API 与界面。

## 自测问题

1. 为什么"实现了什么"不如"在什么条件下会失效"有说服力？
2. 架构图应该画几层？画太细和太粗各有什么问题？
3. 评测集只有 14 条，报告里必须同时写什么，才不会误导读者？
4. Demo 脚本为什么要区分"花钱"和"不花钱"的步骤？
5. 如果面试官问"混合检索真的比单路好吗"，你根据现有数据应该怎么回答？
