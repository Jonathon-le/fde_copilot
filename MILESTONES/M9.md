# M9：观测与评测

> 2026-11-18 完成：trace 落库与四个接口埋点、`/traces` `/metrics/summary`、Streamlit 观测页、相关性门槛校准（结论：不可分，默认关闭）、`tests/` 8 个测试、`data/eval/report.md` 脚本生成。

> 预计 10-15 小时。目标：让每一次调用**可回看**（trace）、让"检索好不好"**可量化**（评测报告），
> 并用自动化测试把回归挡住。

## 先理解：为什么前八个里程碑之后才做这层

M0–M8 一直在"加功能"，每次验证靠手跑代码片段。这有两个后果：

| 问题 | 具体表现 |
|---|---|
| 出错只能复现 | 用户反馈"答错了"，你没有任何现场记录，只能猜 |
| 改动没有护栏 | 换个阈值、改个 prompt，不知道是变好还是变坏 |
| 靠记忆验收 | 每次都要重新贴一遍 TestClient 片段 |

观测与评测不是"附加功能"，是**让前面的东西可以被判断**。

## 任务

### 1. trace 落库

```sql
traces(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  kind TEXT,          -- ask / ask_stream / agent_chat / agent_confirm
  session_id TEXT,
  query TEXT,
  status TEXT,        -- ok / refused / pending / error
  latency_ms INTEGER,
  steps INTEGER,      -- Agent 的工具步数
  payload TEXT,       -- 结构化摘要（命中、引用数、错误类型）
  created_at TEXT
)
```

**要求**

- 记录**摘要**，不记录全文答案：trace 是诊断用的，不是备份。
- 写 trace 失败**不能影响主请求**（try/except + 日志）。
- 不在 trace 里存任何 header、key、完整异常栈。

### 2. 四个接口埋点

| 接口 | 记录内容 |
|---|---|
| `/ask` | 耗时、命中 top1、引用数、状态（ok/refused） |
| `/ask/stream` | 同上，但**在流结束后**用独立连接写 |
| `/agent/chat` | 步数、是否产生 pending、耗时 |
| `/agent/confirm` | 决策、结果状态、执行的工具 |

**关键坑**：FastAPI 的 `yield` 依赖在路由返回时就关闭连接，而流式响应在返回**之后**才继续生成。
所以流式的 trace 必须自己开一个短连接，不能复用 `Depends(get_db)`。

### 3. 查询接口与页面

```text
GET /traces?limit=50&kind=ask
GET /traces/{id}
GET /metrics/summary
```

`/metrics/summary` 至少给：总数、按 kind/status 分布、延迟 p50/p95。
Streamlit 增加第四个标签页"观测"。

### 4. 相关性门槛（挂账项，本任务给出结论）

**要求**

- 写 `scripts/calibrate_relevance.py`：对 `data/eval/queries.jsonl` 里每条 query 输出
  vector top1 分数、BM25 top1 分数，按类别分组，并判断是否存在可分阈值。
- 门槛实现成**可配置、默认关闭**（`RELEVANCE_MIN_SCORE` 环境变量），因为：
  **在当前 34 chunk / 14 query 的评测集上，absent 与 in-domain 的分数是重叠的。**

实测数据（2026-11-18）：

```text
absent   vector top1: 0.4705 / 0.5488 / 0.5842     BM25: 0 / 0 / 2.885
in-domain vector top1: 0.5728 ~ 0.7399             BM25: 1.252 ~ 10.475
```

`absent` 的最大值（0.5842）高于 `in-domain` 的最小值（0.5728）——**不存在一个能完美分开的阈值**。
这不是实现问题，是数据量太小、语义空间重叠。诚实的做法是：把门槛做成开关、记录校准结论，
而不是拍一个数硬上线。

### 5. 自动化测试 `tests/`

**要求**

- `pytest` 进 `requirements.txt`。
- 测试**不联网、不调模型**：需要模型的地方用 monkeypatch 打桩。
- 每个测试自己建临时数据库（`tmp_path`），不碰 `data/app.db`。
- 至少覆盖：

```text
tokenize 幂等（建索引与查询同一结果）
rrf_fuse 去重 + 排序
状态流转 closed→open 被拒
pending 幂等（approve 两次只建一张单）
越权 confirm → 404
/ask 空 question → 422（打桩 chat）
/tickets 不存在 → 404
```

### 6. 评测报告 `data/eval/report.md`

- 由脚本生成，不手写。
- 内容：检索三模式 hit@1 / recall@k、按类别拆分、门槛校准结论、生成时间。

## 提示与坑

- trace 的 `payload` 用 JSON 字符串，别拆成十几列——字段会变。
- 记录耗时用 `time.perf_counter()`（单调时钟），不要用 `time.time()`（会被系统时间调整影响）。
- p95 在样本少于 20 时意义不大，报告里要注明样本量。
- 测试里打桩 `chat` 要打在**被调用处的模块名**上（`app.api.main.chat`），打 `app.llm.client.chat` 不生效。
- 临时数据库必须先 `init_db()`，否则表不存在；`seed` 不是每个测试都需要。
- 流式 trace 不要在生成器 finally 里再用已经关闭的连接——会报 `Cannot operate on a closed database`。
