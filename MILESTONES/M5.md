# M5：混合检索

> 预计 6-10 小时。目标：在向量检索之外补一条 **BM25 关键词检索**，用 **RRF** 融合两路结果，并做一个能并排对比三路结果的 CLI。做完你能用数据回答「这条 query 为什么向量检索没命中」。

## 先理解：M4 留下的两个坑

M4 收尾时实测到两个现象：

```text
库内问题最高分 0.66，库外问题 0.36   → 分数可分，但没有做门槛
「退款」vs「发票」0.5886             → 短 query 上向量区分力不行
「退款」vs「能把钱还给我吗」0.5175
```

第二条是硬伤。纯向量检索把**语义**压成了一个稠密向量，代价是丢掉了精确的字面信息——型号、订单号、专有名词、"红字发票"这种行业术语，恰恰是向量最容易模糊掉的部分。

BM25 正好相反：它只看字面重叠，完全不懂语义，但在精确词命中上非常可靠。

```text
             语义近           字面命中
向量检索      ✓✓✓             ✗
BM25          ✗               ✓✓✓
```

所以不是"谁替代谁"，是**两路互补，融合排序**。

## 任务

### 1. 分词器 `app/rag/tokenizer.py`

```python
def tokenize(text: str) -> list[str]:
    """把中文文本切成检索用的词元。"""

def tokenize_many(texts: list[str]) -> list[list[str]]:
    """批量分词，供建索引用。"""
```

**要求**

- 用 `jieba.lcut()`（返回 list），不要用生成器版本。
- **统一小写 + 去掉标点和空白词元**。同一个词出现在不同大小写/带标点的位置，必须变成同一个 token，否则 BM25 认不出来。
- **加一份停用词表**（"的、了、是、在、和、有、就"这类）。写死在模块里的小集合就够，不用找完整词表。
- **建索引和查询必须调用同一个 `tokenize`**。这是本任务最容易出错的地方：索引侧用 `jieba.lcut`、查询侧忘了处理小写，召回率会莫名其妙掉一半，而且不报错。

**为什么单独一个模块**：分词规则一旦分叉，BM25 就废了。把它收成一个入口，让"分叉"在结构上不可能发生。

**要求**

### 4. RRF 融合 `app/rag/hybrid.py`

```python
def rrf_fuse(ranked_lists: list[list[dict]], *, k: int = 60, top_k: int = 4) -> list[dict]:
    """按 RRF 融合多路有序结果。"""

def search_hybrid(query: str, *, top_k: int = 4, mode: str = "hybrid") -> list[dict]:
    """mode: "vector" | "bm25" | "hybrid"。"""
```

**RRF 公式（自己实现，就三行）**

```text
score(d) = Σ_over_lists  1 / (k + rank(d))
rank 从 1 开始
```

**要求**

- 用 **chunk 的唯一标识**去重，不是 `text`——两段不同 chunk 可能正文相同（重叠窗口）。用 `doc_id::chunk_index` 和库里主键对齐。
- 融合后的 hit 保留完整 7 键；`score` 换成 RRF 分数。**注意此时 score 的量纲已经变了**，不再是 0~1 的余弦相似度，别拿它和 M4 的 0.66 比。
- 可选：额外保留 `vector_score` / `bm25_score` 两个字段，方便 `--show-context` 对比。这对接下来的调试很有用。

### 5. 对比 CLI `scripts/retrieval_compare.py`

```text
python -m scripts.retrieval_compare "退款多久到账"
python -m scripts.retrieval_compare "红字发票怎么开" --top-k 5
python -m scripts.retrieval_compare "..." --json
```

输出建议：**以融合结果为骨架**，每行一个 RRF 命中，并标出它在两路里各排第几。

```text
query: 红字发票怎么开    top_k=3    候选池=20

#   chunk                          RRF      向量名次   BM25名次
1   发票与报销 / 4. 红字发票         0.03279      1         1
2   发票与报销 / 6. 其他说明         0.03175      4         2
3   发票与报销 / 1. 发票类型         0.03151      2         —

只被向量命中：发票与报销 / 5. 报销提示 ...
只被 BM25 命中：—（无）
```

**为什么不用「三列并排、同一行同一 chunk」**：三路是**各自独立排名**的，向量第 2 名和 BM25 第 2 名根本不是同一篇文档。硬按行对齐会让人误读成"这三个是同一个 chunk"。以融合结果做骨架，每行才有确定的含义：**这一条在两路里各排第几**，正好回答"它凭什么排在第一位"。

**要求**

- 两路候选池用 `candidate_k = max(top_k*3, 20)`，融合用 `rrf_fuse([vec_hits, bm25_hits], top_k=top_k)`，**不要在 CLI 里重写融合逻辑**。
- 名次列：没出现在该路候选池里就显示 `—`。
- 额外打印两个差集：只被向量命中、只被 BM25 命中的条目（这是最有价值的信息）。
- `--json` 输出机器可读结构，便于以后接评测脚本。
- 退出码 0；参数错误 2；索引为空 1。
- 不调用 LLM，不联网。

## 提示

- **先别写融合。** 先把 `tokenize` + `search_bm25` 跑通，用 `--retrieval-only` 的心态单独看 BM25 的命中，确认它在你熟悉的 query 上是对的。
- 实测 `jieba.lcut` 的真实输出（jieba 0.42.1）：

```text
退款多久到账        → ['退款', '多久', '到', '账']      ← "到账"被拆了
红字发票怎么开      → ['红', '字', '发票', '怎么', '开']  ← "红字发票"被拆成"红"+"字"+"发票"
积分可以抵扣退款金额吗 → ['积分', '可以', '抵扣', '退款', '金额', '吗']
```

  也就是说，**默认词典会把业务术语切碎**，索引侧和查询侧都会碎——好在两侧碎法一致，BM25 仍能对上。真正要担心的是「本是一个词的被碎成单个字」导致 IDF 失真。用 `jieba.add_word("到账")`、`jieba.add_word("红字发票")` 补词表，然后**对比补词前后 BM25 的命中变化**，这本身就是 M5 的一个小实验。
- BM25 的 IDF 在**小语料**上不稳（只有 34 个 chunk，某些词只在 1 个 chunk 出现，IDF 会飙得很高）。这不是 bug，但要知道：库越小，BM25 越"激进"。
- `BM25Okapi.get_scores(tokenized_query)` 返回的是**每个文档一个分数**的数组，和语料顺序对齐。
- 融合前两个列表的顺序必须是"已按各自分数降序"，RRF 只用 rank，顺序错了结果全错。
- RRF 的 `k` 越大，排名靠后的文档分差越平缓；`k=60` 是论文里的经验值，先照抄，别急着调。
- **别把两路分数相加。** 余弦在 0~1，BM25 可以是 0~30，量纲不同，加权就是在给 BM25 单方面加权。
- 混合不是万能的：两路都错的时候，融合还是错。RRF 只解决"一路对一路错"的情况。
- 评测集里**一定要有几条"库里没有"的问题**，否则你测出来的是"谁更能瞎匹配"，而不是检索质量。
